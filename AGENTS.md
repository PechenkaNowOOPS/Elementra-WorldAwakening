# AGENTS.md — правила для Codex

Ты разрабатываешь **Elementra / World Awakening** — связующую PvE-систему Minecraft-сервера, а не новый самостоятельный игровой дизайн. Основной нормативный документ: `docs/awakening.md`. Если инструкции конфликтуют, запрос владельца проекта и последняя утверждённая документация имеют приоритет над промежуточными черновиками.

## Технический контекст

- Minecraft Java Edition, целевая серверная платформа Purpur/Paper **26.2**, Java **25**.
- Без обязательных клиентских модов. Resource pack допустим как необязательная презентация с fallback.
- Не переписывай существующие модули без анализа их реального API и состояния исходников.
- Новые функции — модульно и с ясным владением доменными данными.
- Не добавляй крупные расширения ради ЗБТ: этап предназначен для стабильности и баланса ядра.

## Игровые инварианты (не меняй самовольно)

1. Ровно **4** обязательных Печати: `FIRE`, `WATER`, `EARTH`, `AIR`. Четыре соответствующих босса; их названия/боевые фазы пока не утверждены.
2. Одна уникальная Печать на стихию; произвольный порядок прохождения.
3. Победа в рейде **не** изменяет мир напрямую: только подтверждённая устойчивая активация Ядра.
4. `threatStage = count(unique committed mandatory seals)`, в диапазоне 0–4.
5. Стихийные способности мобов открываются **только** для реально активированных стихий.
6. Незер открывается после коммита **всех четырёх** обязательных Печатей, а не по пустому списку/настройке порога.
7. Новички, регионы, безопасные зоны защищены от слепого глобального усиления.
8. Не пересчитывать уже появившихся мобов или уже начатые рейды при очередной Печати.
9. Система не требует принадлежности к народу FourNations и не меняет его способности.
10. Усиление не должно затрагивать животных HuntingGrounds, питомцев, неразрешённых мобов или данжи без явного разрешения.

## Владение данными

- `NetherSeals`: алтарь/босс/право победы/установка Ядра/устойчивая активация, outbox.
- `WorldProgression`: глобальное состояние, идемпотентное применение события, immutable snapshot, правило доступа в Незер.
- `MobDifficulty`: разрешённые спавны, профили регионов, стадии и стихийные варианты, защита от двойного баффа.
- `Regions`: собственная классификация/защита зон.
- `FourNations`, `HuntingGrounds`, `Dungeons`: не мутировать их данные и правила скрытно.

## Стандарты реализации

- Прежде чем менять код, проверь актуальные исходники, ветку, фактические контракты и тесты. При отсутствии зависимостей создай заглушку **интерфейса**, а не выдумывай чужую реализацию.
- Не утверждай успешную сборку, тест или runtime-готовность без фактического выполнения.
- Не выполняй синхронные SQL-операции или полный обход всех мобов в событиях спавна/тика.
- Сохраняй метку уже применённого профиля в PDC/аналогичном постоянном механизме.
- Проверяй защиту от повторов (`operationId`, `sealId`), crash/reload, invalid config и отсутствие дюпов.
- Внутрисерверные действия по умолчанию через NPC, книги, алтари и GUI; админ-команды только диагностические/служебные с аудитом и правами.
- Любой коэффициент, шанс и порог, помеченный как **ПЛЕЙТЕСТ/ПРОЕКТ**, должен оставаться конфигурируемым и не объявляться утверждённым.
- Не размывай границу между требованиями, исходниками, компиляцией, тестами и интеграцией на сервере.
- При любом поведении, способном нарушить прогрессию, применяй fail-closed для порталов.

## Проверки, которые обязаны появиться в коде

- 16 комбинаций четырёх стихий, стадия и условие открытия Незера.
- Дубликаты событий/активаций, порядок событий, пропущенные/невалидные ID и пустой список Печатей.
- Сбой после локального коммита NetherSeals, но до коммита WorldProgression, с восстановлением доставки.
- Применение баффа к одному мобу только один раз, включая выгрузку/загрузку чанка и рестарт.
- Исключения HuntingGrounds/данжей/боссов/админских спавнов.
- Корректность региональных коэффициентов, ограничения атрибутов и шансов категорий.
- Нельзя открыть Незер при 3/4, повреждённой конфигурации и обходным телепортом.

## Стандарт выполнения каждой задачи

1. Прочитать релевантный раздел `docs/awakening.md` и `docs/decisions.md`.
2. Указать, какие файлы меняются и чей модуль владеет новым поведением.
3. Внести минимальное совместимое изменение, сохранить остальные механики.
4. Добавить автономные тесты, а для интеграции определить тестовый сценарий на Purpur.
5. Прогнать доступные проверки, честно сообщить результаты/блокеры.
6. Актуализировать `docs/backlog.md` и перечень принятых решений **только после утверждения**.

Не начинать с создания новых стихий, пятой Печати, новых систем наград, линейных квестов или обязательного гринда.
